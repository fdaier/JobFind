# DRAFT — JobFind 高容量申请看板方案

> 状态：待确认；本文件不是已批准的实施规范。
> 日期：2026-09-15

## 要解决的问题

当“已投递”等单一阶段累积大量岗位时，用户面对的是三个不同但叠加的困难：

1. **定位困难**：已知公司或岗位名称时，只能在同样式的卡片中纵向扫读。
2. **行动困难**：需要处理的风险、临近时间和普通历史岗位没有明确优先级，真正要处理的事项容易被淹没。
3. **空间困难**：单列自然向下生长，会把整张十阶段看板拉得很长；浏览一个长列时，其他阶段的状态不再保持在视野中。

这不是删掉历史或把岗位移出“已投递”的问题。历史申请仍应完整保留，用户需要的是更快地找到它、判断它是否仍值得处理，并保持对全局流程的视野。

## 设计方向

**视觉主张：** 把看板从一串松散卡片变为一个稳定、可扫描的求职工作台——全局用于找岗位，列内用于处理阶段内的工作。

### 1. 顶部全局检索与工作筛选

在看板上方增加一条低干扰的控制条：

- 搜索框：匹配公司、岗位名称、20 字备注；支持 `/` 聚焦与 `Esc` 清空。
- 快捷范围：`全部`、`需要处理`、`有关键时间`。不新增持久化数据，仅由现有风险、时间与岗位字段实时计算。
- 搜索后保留全部阶段列，但列头显示“匹配数／总数”，例如 `已投递 2 / 27`；不匹配岗位临时隐藏，用户仍能知道结果位于哪个阶段。
- 未找到结果时只显示明确空状态和清除入口，避免用户误以为岗位被删除。

该层解决“我想找腾讯 AI 产品经理”的直接定位问题，而不是要求用户先进入“已投递”再滚动查找。

### 2. 桌面端固定看板工作区与列内滚动

桌面端将看板主体限制在可视工作高度内：

- 十个阶段列维持横向看板；每一列的标题区固定，岗位列表在列内独立纵向滚动。
- 浏览较长的“已投递”列时，其他阶段列和所有阶段标题始终可见。
- 仅在有溢出的列中展示细、低对比度滚动提示；移动端仍使用自然页面滚动，避免嵌套滚动造成操作困难。

这不是缩小内容，而是把“浏览整页”改成“在当前阶段内浏览”，让用户的空间记忆稳定下来。

### 3. 紧凑卡片与阶段内排序

卡片继续保留当前约定的三类信息：关键时间、Agent 风险、备注；但重排为高密度的三行结构：

1. 公司名与岗位名作为唯一主标题；移除卡片内重复的阶段徽标（阶段已由列标题说明）。
2. 关键时间与风险在同一信息行中优先显示；没有风险时保持安静，不撑高卡片。
3. 备注只在已填写时显示，单行截断；详情抽屉仍是完整信息与编辑入口。

默认排序为“优先处理”：临近／过期关键时间、严重风险、一般风险、其余岗位；同级按最近更新排序。控制条提供“最近更新”和“公司名”两个排序选项，便于批量投递后回看。

## 关键交互流程

| 用户意图 | 交互 | 结果 |
| --- | --- | --- |
| 找一条已投递岗位 | 输入公司／岗位／备注 | 看板立即显示各阶段的匹配岗位与匹配数，点击卡片进入详情 |
| 只处理今天有动作的岗位 | 选择“需要处理” | 仅保留有临近时间或 Agent 风险的岗位；历史记录仍未删除 |
| 浏览已投递历史 | 在“已投递”列中滚动 | 列标题、其他阶段和顶部检索始终保持可达 |
| 批量投递后确认最新条目 | 排序选择“最近更新” | 该列按更新时间降序，数据不被改写 |

## 边界与数据安全

- 不迁移、删除、隐藏持久化岗位；搜索、筛选、排序都是内存中的派生视图。
- 不改变现有十阶段、时间线、备注、材料关联或删除语义。
- 不引入账号、后端或真实 LLM；匹配使用本地规范化文本包含规则。
- 用户未搜索／筛选时，仍能浏览全部岗位；任何筛选状态均有清晰的可见标签与一键清除。

## 验收标准

1. 已投递有 30 条岗位时，用户可通过公司、岗位名或备注在一次输入后定位结果，无需手动滚动扫描。
2. 桌面端长列不再拉长整页；列标题固定，阶段间的全局状态始终可见。
3. 紧凑卡片仍在不打开详情的情况下展示关键时间、风险和已填写备注。
4. “需要处理”只使用现有时间／风险字段计算，不影响任何岗位的保存值。
5. 搜索、筛选、排序、卡片点击、现有阶段推进与删除回归通过；旧 localStorage 数据保持不变。
