# Draft PRD：申请看板流程、备注与岗位详情编辑（V3）

> 状态：待用户确认，尚未开始产品实现。  
> 日期：2026-09-14  
> 数据原则：本期绝不重置、覆盖或丢弃既有浏览器 localStorage 中的岗位、JD、材料、时间线与面试复盘数据。

## 1. 背景与要解决的问题

现有申请看板沿用七阶段通用漏斗，缺少校招中常见的测评及多轮面试；卡片把“材料完成度”放在过高层级，反而遮蔽真正影响推进的时间、风险和临时备注。

此外，真实 JD 导入后的岗位虽然可在 Agent 作战台中推进或删除，但岗位详情的业务信息以只读方式呈现，无法纠正录入错误或补充后续信息。

## 2. 当前“关键词”功能的真实工作方式

当前实现**没有调用 LLM、外部 API 或语义模型**。它在浏览器本地运行：

1. 用一组固定词表在 JD 文本中做大小写不敏感的字面匹配，例如 `LLM`、`Agent`、`RAG`、`数据分析`、`用户洞察`。
2. 以少量正则判断“简历”“作品集”等材料建议。
3. 将命中的词和材料建议作为可编辑的预览结果保存。

因此它不会理解上下文、岗位要求与加分项的区别、词语的重要性或同义表达；像“AI”“增长”这样的宽泛词尤其容易造成噪声。这正是体验上“判断并不是很好”的根因，不是用户输入错误。

### 本期建议：先做可信的 P0，而不假装它是智能判断

- 文案从“关键词”调整为“JD 命中的术语（可编辑）”。
- 依据 JD 的“职责／岗位要求／加分项”分段，标注术语来自哪一段；岗位要求优先，加分项明确标作“加分”。
- 移除过宽的单词规则（如独立的“AI”“增长”“原型”），改用边界明确的技术、产品方法和业务领域词典，并保留对应原文短句，方便用户核对。
- 继续允许用户在预览页和岗位详情的基本信息页增删、修改这些术语，用户填写的内容始终优先。

这仍是可解释的本地辅助，不能替代语义理解。若要做 P1“真正从 JD 推理重要能力与匹配度”，需要新增服务端模型调用、供应商/API Key、费用控制与 JD 隐私告知；应在单独确认后实施，并保证模型失败时仍可用本地录入保存岗位。

## 3. 申请流程与看板

### 3.1 阶段顺序

移除“关注中”，统一使用以下十个校招流程列：

| 顺序 | 内部阶段 | 展示名称 |
| --- | --- | --- |
| 1 | `to_apply` | 待投递 |
| 2 | `applied` | 已投递 |
| 3 | `assessment` | 测评 |
| 4 | `written_test` | 笔试 |
| 5 | `first_interview` | 一面 |
| 6 | `second_interview` | 二面 |
| 7 | `third_interview` | 三面 |
| 8 | `hr_interview` | HR面 |
| 9 | `offer` | 录用 |
| 10 | `rejected` | 已淘汰 |

“录用”和“已淘汰”仍是终态；删除入口仍在岗位详情底部，所有阶段都可删除，沿用二次确认。阶段推进仍会写入时间线。详情底部改为一个主要的“推进到下一阶段”操作，加上低强调的“调整阶段”选择器，以保留跳过测评或某一轮面试的纠正能力，避免十多个推进按钮挤满底部。

### 3.2 卡片信息层级

每张看板卡片只保留以下三类行动信号：

1. **关键时间**：DDL、测评／笔试／面试等最近的关键节点；无则显示“暂无关键时间”。
2. **Agent 风险**：已有确定性风险标签；无风险时显示“暂无风险”。
3. **备注**：展示用户的短备注；未填写时显示“未添加备注”。

移除卡片中的材料完成度、百分比和进度条。材料状态保留在岗位详情的“材料”页，避免把已投递岗位的常规完成情况占用看板注意力。

十列看板仍使用横向滚动；卡片改为轻量、纵向的三信号摘要，而不是进一步压缩成难读的指标格。视觉上维持当前中性色工作台和清晰的流程节奏，删除与阶段纠正保持低强调。

### 3.3 备注

- 每个岗位新增一条纯文本“备注”，上限 **20 个字符**，显示实时字数；用于如“等内推回复”“已约明早测评”等快速上下文。
- 备注在“基本信息”页编辑，并始终在看板卡片上可见，无需打开详情。
- 备注为空不视为风险、不创建 Agent 任务，也不影响原有材料、时间线或面试复盘。

## 4. 岗位详情中的编辑入口

保留图示的详情抽屉及五个标签页。**Agent 作战台只读**：它是根据其他字段生成的建议，不应被手工改写。其余四个标签页在标题右侧提供低强调的“编辑”入口，点击后仅将当前页切为编辑态，底部出现“取消／保存”。保存后 Agent 自动根据最新数据重新计算。

| 标签页 | 可编辑内容 | 保存行为 |
| --- | --- | --- |
| 基本信息 | 公司、岗位名称、当前阶段、DDL、JD 正文、JD 术语、职责/要求、联系人、批次、渠道、备注 | 校验公司、岗位与 JD；手动调阶段会新增时间线记录，不覆盖历史 |
| 材料 | 所需材料、已绑定的材料 | 双向更新岗位与材料的关联，不创建或删除用户的材料条目 |
| 时间线 | 添加、修改、删除时间线事件的日期、阶段和说明 | 阶段推进新增事件而非覆盖既有事件；删除前二次确认 |
| 面试复盘 | 新增、修改、删除复盘条目 | 保留现有复盘数据，删除前二次确认 |

编辑态不在每个字段旁常驻按钮，避免页面显得像配置表；未编辑时维持易扫读的摘要。关闭抽屉或点击取消均放弃仅本次未保存的草稿。

## 5. 既有数据迁移与保护方案

阶段枚举变化不能直接用新校验规则读取旧数据，否则现有 localStorage 可能被判为无效。本期实施必须先做兼容迁移：

| 旧阶段 | 新阶段 | 说明 |
| --- | --- | --- |
| `interested` | `to_apply` | “关注中”并入待投递 |
| `to_apply` | `to_apply` | 不变 |
| `applied` | `applied` | 不变 |
| `written_test` | `written_test` | 不变 |
| `interviewing` | `first_interview` | 保留既有面试记录，默认映射至一面；用户可在详情中纠正 |
| `offer` | `offer` | 不变 |
| `rejected` | `rejected` | 不变 |

实施要求：

1. 首次迁移前，将原始岗位 JSON 写入一次性备份键（例如 `jobfind.jobs.backup.v3`），再按上表转换岗位阶段和每条时间线阶段。
2. 为旧岗位补充空备注字段，但不改变岗位 ID、JD、材料关联、联系人、DDL、时间线内容、面试复盘、创建/更新时间。
3. 新旧结构均能被读取；无法识别的原始条目不以“校验失败”为理由清空整个岗位数组，需保留原始数据并给出可恢复路径。
4. 不变更 demo 数据版本，不运行任何“恢复示例数据”逻辑；仅在用户浏览器实际打开新版本时做一次幂等迁移。

## 6. 实施范围与验证

确认后会同步更新正式 spec、计划、类型、规则引擎、存储校验、看板、详情抽屉、仪表盘/复盘统计及测试夹具；不会接入自动投递、账号系统、云同步或 LLM。

至少验证：

- 已有岗位的完整 localStorage 快照迁移后，岗位数量、ID、JD、材料绑定、时间线、复盘和关键日期均保持；阶段只按上表变化，且存在原始备份。
- 十列顺序、阶段推进、终态删除和 Agent 规则均按新阶段工作。
- 卡片不再出现“材料完成度”，而正确显示关键时间、风险和备注。
- 备注的 20 字限制、保存和卡片即时更新可用。
- 四个非 Agent 标签页的编辑、取消、校验、保存和删除确认可用；Agent 建议随保存后的资料刷新。
- 完整测试、类型检查、lint、静态构建、本地浏览器流程及上线域名回归通过。
