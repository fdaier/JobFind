# JobFind 核心闭环设计文档

## 1. 决策摘要

JobFind Stage 1 要先构建一个面向面试演示的核心闭环原型，而不是一次性做完 PRD 中的全部功能。第一阶段要证明的核心产品判断是：JobFind 不是另一个求职记录表格，而是面向学生求职季的 AI 求职项目经理。

已经确认的演进顺序是：

1. Stage 1：A - Core Loop Prototype，核心闭环原型。
2. Stage 1.1：C - Agent Deepening，Agent 能力深化。
3. Stage 1.2：B - Full MVP Completion，完整 MVP 补齐。
4. Stage 2：LLM Agent Upgrade，真实模型能力增强。

第一轮编码只启动 Stage 1。后续阶段需要被数据结构、规则引擎和组件边界支持，但不应该在 Stage 1 中提前完整实现。

## 2. 产品目标

构建一个可演示的 JobFind 原型，让评审能在 3 分钟内理解“学生的 AI 求职项目经理”定位，并能在 1 分钟内看完核心流程：

```text
粘贴 JD -> 生成岗位卡 -> 识别风险 -> 生成今日行动
```

这个原型应该具备真实产品质感，但第一责任是清晰传达产品判断、AI 设计逻辑和 MVP 取舍。

## 3. 用户与定位

目标用户是正在找实习或校招岗位的学生，尤其是同时管理多个机会、多个 DDL、多份材料和多轮面试的人。

他们的核心任务不是“再找一个岗位信息”，而是“管理一个持续数周到数月的求职项目”。因此 JobFind 的产品表达要围绕掌控感、风险判断和下一步行动，而不是围绕记录字段本身。

定位句：

> JobFind 帮助学生把分散的岗位、材料、截止日期和面试节点转化成清晰的下一步行动。它不是另一个求职表格，而是学生的 AI 求职项目经理。

## 4. Stage 1 范围

Stage 1 包含：

- 今日求职作战台，作为 Dashboard 首屏。
- 申请看板，按 7 个阶段展示岗位。
- 岗位详情抽屉，从岗位卡片打开。
- 规则型 JobFind Agent，用于风险识别和今日任务规划。
- JD 解析 Dialog，支持模拟解析、预览和保存。
- 8 条真实感岗位样例和 6 条材料样例。
- 岗位卡片和岗位详情中的材料完整度检查。
- localStorage 保存轻量状态。
- 中文 UI，AI、JD、HR、DDL、Offer、Boss 等常见术语保留英文。
- 浅色模式、桌面端优先。

Stage 1 不包含：

- 真实 LLM API。
- 登录、后端、数据库或账号系统。
- 真实文件上传。
- 拖拽看板。
- 浏览器插件、邮件同步、日历同步或招聘平台接入。
- 完整材料中心深交互。
- 完整渠道复盘和策略分析。
- 复杂移动端适配。

## 5. 信息架构

### 5.1 首页：今日求职作战台

首页不是营销页，也不是普通表格。用户打开后应直接看到当前求职状态、今日优先任务和主要风险。

必需模块：

- 状态摘要：本周投递、待处理任务、高风险申请、即将面试。
- 今日优先任务：展示 3 到 5 条按紧急度和影响度排序的行动。
- 迷你申请看板：紧凑展示各阶段岗位分布。
- 风险雷达：展示 DDL、材料缺口、面试准备、长期无反馈等风险。
- 简化申请漏斗：作为后续策略复盘方向的轻量信号。

### 5.2 申请看板

看板按阶段分组展示岗位：

- 感兴趣。
- 待投递。
- 已投递。
- 笔试 / 测评。
- 面试中。
- Offer。
- 拒绝 / 归档。

Stage 1 不做拖拽。点击岗位卡片打开详情抽屉；阶段推进可以在详情抽屉中由用户确认触发。

每张岗位卡片必须展示：

- 公司。
- 岗位。
- 当前阶段。
- DDL 信息。
- 风险标签。
- 材料完整度。

### 5.3 岗位详情抽屉

岗位详情从右侧 Sheet 打开，保留看板上下文。详情内部使用 Tabs，避免在有限宽度内堆叠过多信息。

必需 Tabs：

- 基本信息：公司、岗位、JD、关键词、要求、联系人。
- 时间线：申请与阶段变化记录。
- 材料：已绑定材料和缺失材料类型。
- AI 建议：动作、原因、优先级和可确认下一步。
- 面试记录：轮次、时间、问题、复盘、结果。

### 5.4 JD 解析 Dialog

JD 解析是一个聚焦流程：

```text
打开 Dialog -> 粘贴 JD -> 解析 -> 预览生成岗位卡 -> 保存到看板
```

Stage 1 可以使用固定样例 JD 和确定性解析逻辑。保存解析结果后，新岗位必须加入看板，并参与风险计算和今日任务生成。

## 6. 规则型 Agent 设计

Stage 1 的 Agent 不是聊天窗口，也不调用模型 API。它是一个确定性的产品 Agent 层，用规则模拟“感知、诊断、规划、用户确认执行”。

### 6.1 Context Engine：感知申请池

读取当前申请池信息：

- 岗位。
- 阶段。
- 网申截止时间。
- 笔试 / 测评时间。
- 面试时间。
- 投递时间。
- 所需材料。
- 已绑定材料。
- 来源渠道。

用户侧表达示例：

> 当前有 8 个申请，其中 3 个需要优先处理。

### 6.2 Risk Engine：诊断风险

使用确定性规则生成风险标签：

- DDL 在 24 小时内：critical。
- DDL 在 3 天内：warning。
- 所需材料未绑定：warning。
- 面试在 3 天内：critical。
- 已投递 10 天以上无反馈：warning。

风险标签必须影响今日任务排序，不能只是视觉装饰。

### 6.3 Planning Engine：生成今日任务

把风险转成用户行动，并按优先级排序。今日任务最多展示 5 条。

任务映射：

- 紧急 DDL 风险 -> 立即处理投递或截止事项。
- 材料缺口 -> 绑定或准备缺失材料。
- 面试准备风险 -> 准备对应面试轮次。
- 长期无反馈 -> 跟进 HR 或联系人。

每条任务必须包含：

- 动作。
- 原因。
- 优先级。
- 关联岗位。
- 动作类型。
- 完成状态。

### 6.4 Action Layer：用户确认后执行

Agent 负责建议，用户负责确认。Stage 1 动作包括：

- 标记任务完成。
- 保存 JD 解析生成的岗位卡。
- 推进岗位阶段。
- 查看建议依据。

Agent 不得自动投递岗位、发送消息、上传文件或在未经确认的情况下修改状态。

## 7. 样例数据要求

Stage 1 需要包含 8 条岗位：

| 公司 | 岗位 | 阶段 | 核心演示点 |
|---|---|---|---|
| 腾讯 | 产品策划实习 | applied | DDL 当日截止，作品集未绑定 |
| 字节跳动 | AI 产品经理实习 | interviewing | 明天一面，需要准备面试 |
| 小红书 | 产品运营实习 | applied | 已投递 12 天无反馈 |
| 美团 | 产品经理（校招） | written_test | 笔试已通过，等待面试通知 |
| 阿里巴巴 | 产品实习 | interested | DDL 5 天后，还未投递 |
| 网易 | 游戏策划实习 | offer | 已拿 Offer，需要决策 |
| 京东 | 产品运营 | rejected | 被拒，归档参考 |
| 快手 | 产品经理实习 | to_apply | 待投递，材料齐全，正常状态 |

Stage 1 需要包含 6 条材料：

| 材料 | 类型 | 方向 | 版本 | 演示作用 |
|---|---|---|---|---|
| 产品经理简历 | resume | 产品经理 | v2.3 | 绑定产品岗 |
| 运营方向简历 | resume | 产品运营 | v1.8 | 绑定运营岗 |
| AI 产品作品集 | portfolio | 产品经理 | v1.2 | 腾讯缺失，字节已绑定 |
| 本科成绩单 | transcript | 通用 | 2025 春 | 用于正式申请 |
| 游戏策划作品集 | portfolio | 游戏策划 | v1.0 | 绑定网易 |
| CET-6 证书 | certificate | 通用 | 2025 | 作为辅助证书 |

日期应相对当前日期动态生成，确保演示在不同日期打开时仍能保持正确风险状态。

## 8. Stage 1 验收标准

Stage 1 完成时必须满足：

1. 打开首页后，无需解释也能看到今日优先任务、风险雷达和岗位阶段分布。
2. 看板页能看到 8 个岗位卡片，分布在 7 个阶段中。
3. 岗位卡片展示公司、岗位、阶段、DDL、风险标签和材料完整度。
4. 点击岗位卡片能打开右侧详情抽屉。
5. 详情抽屉包含基本信息、时间线、材料、AI 建议和面试记录。
6. 腾讯样例能展示“DDL 当日截止 + 作品集未绑定”风险。
7. 字节样例能展示“明天一面 + 面试准备建议”。
8. 小红书样例能展示“已投递 12 天无反馈 + 跟进建议”。
9. 粘贴样例 JD 后能生成岗位卡预览。
10. 保存解析结果后，新岗位进入看板，并参与风险和任务计算。
11. 今日任务最多展示 5 条，并按规则优先级排序。
12. 标记任务完成后，界面状态更新并持久化到 localStorage。
13. Stage 1 不依赖后端、登录、数据库、模型 API 或文件上传。
14. UI 文案明确表达：Agent 负责诊断和规划，用户确认后执行。
15. 演示脚本能顺畅走完：首页 -> 看板 -> 腾讯详情 -> JD 解析 -> 保存岗位 -> 回到今日任务。

## 9. Stage 1.1：Agent 能力深化

Stage 1.1 在 Stage 1 核心闭环可用之后进行。

目标：让 Agent 差异化更清楚，而不是马上扩展所有产品功能。

可增加：

- 显式 Agent 推理链路：感知 -> 诊断 -> 规划 -> 确认执行。
- “为什么先做这件事？”的任务排序解释。
- 长期无反馈岗位的跟进话术草稿。
- 基于岗位要求的面试准备清单。
- 材料补齐建议，明确指出缺失材料。
- Agent 面板文案强调它是求职项目经理，不是聊天机器人。

Stage 1.1 验收标准：

- 每条建议都能回答“为什么现在重要”。
- 用户能看到 Agent 排序依据。
- Agent 仍然保持用户确认执行，不自动做外部动作。
- 规则型实现仍然可接受，LLM API 不是必需项。

## 10. Stage 1.2：完整 MVP 补齐

Stage 1.2 在 Agent 差异化更清楚之后进行。

目标：补齐产品面，让 JobFind 更接近完整 MVP。

可增加：

- 完整材料中心页面。
- 更清晰的申请漏斗。
- 渠道复盘卡片。
- 求职健康度。
- 更完整的面试时间线。
- 更完整的演示脚本。

Stage 1.2 验收标准：

- 四个核心界面完整：总览、看板、详情抽屉、材料中心。
- P1 功能服务于 Agent 主线，而不是抢走主线。
- 评审能同时理解“今日执行”和“后续策略复盘”。

## 11. Stage 2：LLM Agent 增强

Stage 2 不属于第一轮实现范围。

后续接入模型时，应保持以下分工：

- LLM 负责非结构化文本理解和自然语言表达。
- 规则负责风险判断、优先级排序和状态更新。
- 用户确认仍然是状态变化前提。

最值得优先接入的模型入口：

- 解析任意 JD 文本。
- 将今日计划改写得更个性化。
- 生成面试准备清单。
- 生成跟进话术草稿。

模型失败时必须回退到规则型 Agent。

## 12. 后续实施约束

实施计划需要保留这些边界：

- 数据类型、样例数据、规则引擎和 UI 组件分离。
- 规则函数尽量保持纯函数。
- localStorage 访问通过小型封装完成。
- Stage 1 不提前实现 Stage 1.1 和 Stage 1.2 的完整功能，只保留扩展友好的结构。
- 优先使用成熟库和官方工具，不自建无必要基础设施。
- 文件保持聚焦，方便后续使用 subagents 或分任务迭代。

建议 Stage 1 技术栈：

- Next.js App Router。
- TypeScript。
- Tailwind CSS v4。
- shadcn/ui。
- React Context + localStorage。
- npm。
