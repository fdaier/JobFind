# JobFind 邮件进度建议与逐条审批设计草案

> 状态：待用户确认，未实施。2026-09-30。依据：`2026-09-30-jobfind-real-mail-recognition-findings-draft.md` 的 51 封入站邮件核查结果。

## 用户目标与边界

收到“投递成功”“测评邀请”“在线笔试”等流程邮件后，JobFind 应提出岗位进度建议；用户点击查看证据，**逐条决定是否应用**。邮件扫描、打开弹窗、忽略建议均不改动岗位。只有点击某条的“应用到看板”才写入该岗位的阶段与时间线。

第一版沿用现有手动“扫描全部／继续扫描”入口；每次扫描后生成或更新待确认队列。后台定时查新邮件不在本草案内，但将来可复用同一队列与审批流程。当前岗位仍以本浏览器 localStorage 为唯一事实源，不借此功能迁移或覆盖岗位。

## 哪些邮件能提出阶段建议

| 邮件中的明确事实 | 建议阶段 | 必要条件 |
| --- | --- | --- |
| 明确确认该岗位投递／简历提交成功 | 已投递 | 不是内推邀请、催投递或招聘宣传 |
| 明确邀请本人完成测评，通常有专属入口 | 测评 | “含链接”仅是佐证，必须有测评通知语义 |
| 明确邀请本人参加笔试／在线考试，通常有作答入口 | 笔试 | 主题主事件优先，不被正文附带的“测评／面试”词覆盖 |
| 明确面试邀约或预约成功 | 一面／明确写出的二面、三面、HR 面 | 泛称“面试”只可从面试前阶段建议到一面，不能自行猜测下一轮 |
| 明确录用或本次申请不再推进 | 录用／已淘汰 | 必须显示高醒目度证据并逐条确认；条件句“若未通过”不算淘汰 |

宣讲会、直播、开放日、内部推荐邀请、邀请投递、体验问卷和泛招聘邮件只保留在邮件列表，不产生进度推进建议。来源域名是辅助线索，不能单独证明发件公司或申请结果。

## 岗位匹配与不倒退规则

- 扫描端只保存受控的事件类型、邮件主题／发件域／时间、命中证据句、提及的公司与岗位及其来源位置；不保存原始正文或专属测试链接。若要在看板保存测试链接，另做需用户确认的设计。
- 在**当前浏览器**用公司正式名／受控别名、正文的岗位名称、已有投递日期共同匹配。公司和岗位均明确命中且只有一个候选时预选；仅公司命中或同公司多岗位时要求用户在弹窗内手动选岗位。演示种子岗位不得仅凭公司名自动预选。
- 若邮件建议阶段等于或早于岗位现阶段，不生成普通“推进”操作；历史回执可显示为“已覆盖”，绝不把笔试中的岗位退回测评。若岗位已是录用／已淘汰而新邮件冲突，单独显示“状态冲突，需人工核对”，不能一键常规应用。
- 同一封邮件以邮箱 UIDVALIDITY＋UID（必要时辅以 Message-ID 哈希）去重；同岗位同事件的重复模板合并为一条建议、保留邮件来源数。批准较晚阶段后，较早且已被覆盖的待批建议自动转“已覆盖”，不要求重复审批。
- 没有足够岗位证据的邮件进入“待匹配”，可由用户选岗位后再审批；不擅自新建岗位。无明确流程结果的邮件只供查看，不显示“应用”。

## 审批弹窗

视觉方向：沿用 JobFind 的浅色、靛蓝与克制的分隔线，把它做成审阅工作台；避免为每封邮件堆卡片或连续自动弹窗。内容顺序是“待处理数量 → 建议列表 → 选中建议的证据与岗位 → 单条操作”。交互仅用轻微选中态切换和批准后的队列收起反馈；尊重减少动态效果设置。

扫描结束后，在状态收件箱显示“发现 N 条待确认建议”与按钮“查看建议”。**不强制弹窗**；用户可稍后从同一入口重新打开。桌面端弹窗左侧是紧凑队列、右侧是当前选中建议的详情；窄屏改为单列。弹窗限制在视口内，内容可滚动，操作区保持可见，避免再次出现必须 F11 才能点击的问题。

```text
邮件进度建议                                      8 条待确认
──────────────────────────────────────────────────────────
待确认列表                 当前建议
京东 · AI 产品经理         已投递 → 笔试
携程 · AI 产品经理         来源：笔试邀请邮件 · 日期 · 发件域
网易 · 待选择岗位         依据：“邀请您参加在线笔试……”
                           匹配岗位：[京东 · AI 产品经理 ▾]
                           说明：邮件提到岗位名称，非仅凭域名推断
──────────────────────────────────────────────────────────
             暂不处理        忽略这条        应用到看板
```

每条建议展示当前阶段 → 建议阶段、邮件主题、时间、发件域、一句**命中的脱敏证据**以及为什么匹配该岗位。用户可在应用前改选岗位；无法唯一匹配时必须先选择。三个动作的语义分别是：

- **应用到看板**：仅对当前一条生效，写入阶段及带邮件来源标识的时间线；批准下一条仍需再次点击。
- **忽略这条**：记住处理决定，重复扫描不再提醒；不改岗位。
- **暂不处理**：保留待确认，关闭弹窗或切换下一条；不改岗位。

不提供“全部应用”按钮。阶段之外的截止时间本期先展示为核对信息，**不随阶段审批一并写入**；这样不会把“建议 48 小时内”和硬截止混为一谈。

## 数据安全、持久化与失败恢复

- 服务端新增按用户隔离、启用 RLS 的邮件事件／处理决定记录；GET 可重新取回待确认队列。扫描只追加或更新事件，不写岗位。候选名单和当前阶段从本浏览器岗位派生，不上传完整 JD／材料，也不清空旧 localStorage。
- 首次邮件驱动的岗位变更前，新增一次性原始岗位备份（独立于 `jobfind.jobs.backup.v3`）。申请时重新读取该岗位的最新阶段，防止弹窗打开后手动编辑导致覆盖；将邮件事件 ID 随时间线一起写入岗位，重复点击与重试必须幂等。
- 先确保本地岗位写入成功，再把该事件标为服务端“已应用”；若服务端回执失败，客户端凭时间线事件 ID 显示“已应用、待同步”，重试回执而不重复推进。忽略决定由服务端持久化；失败时仍留在待确认。
- 当前版本无跨设备岗位同步。在没有这些岗位的另一个浏览器，邮件事件可见，但“应用到看板”必须禁用并说明原因；绝不能基于演示岗位悄然应用。

## 验收要点

1. 真实投递、测评、笔试邀请产生对应建议；宣传／问卷、条件句“若未通过”不产生错误推进。
2. 同公司多岗位必须用正文岗位或用户手选；历史邮件不会让当前阶段倒退，终态冲突必须单独核对。
3. 扫描后按钮显示待确认数；关闭／重开弹窗、刷新页面后队列与已处理决定保持正确；无自动强制弹窗与批量批准。
4. 每次只应用用户点击的那一条，时间线可追溯来源；重复扫描、重复点击、API 失败重试不造成重复推进。
5. 全流程不修改已有岗位，直到用户点“应用到看板”；首次应用有独立备份，旧 `jobfind.jobs.backup.v3` 不被覆盖。

## 待用户确认的范围

建议先交付上述“手动扫描 → 待确认队列 → 单条审批 → 看板更新”闭环。后台定时扫描、自动写入测评／笔试截止时间，以及广告邮件文件夹纳入扫描，均先不包括在本期；可以在闭环验证后分别增加。
