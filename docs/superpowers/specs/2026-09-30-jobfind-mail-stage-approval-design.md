# JobFind 邮件进度建议与逐条审批正式设计

> 2026-09-30 用户确认 `2026-09-30-jobfind-mail-stage-approval-flow-draft.md`，并补充：所有相关招聘邮件先可见；存疑邮件独立成栏，允许手动选岗位和阶段后应用。

## 产品闭环

手动扫描 163 收件箱 → 保存招聘相关邮件的脱敏观察；未识别邮件只保留主题／发件人／时间等最小元信息 → 在状态收件箱展示“进度建议”和“待核对”两栏 → 用户点击“查看与处理”打开受视口约束的审阅弹窗 → 对单封邮件选定岗位、核实当前与目标阶段 → 逐条应用／忽略／暂不处理。扫描和分类绝不静默改写看板。

“进度建议”仅包含明确的投递成功、测评、笔试、面试、录用、淘汰通知，并且岗位匹配唯一且阶段可前进。“待核对”保留其他招聘相关邮件、未识别邮件，以及目标阶段／岗位存疑或与现状冲突的邮件；给用户可见的手动岗位与阶段选择器，只有用户明确选择并点击“应用”才更新看板。未识别邮件可能与求职无关，不预选目标阶段。宣传类邮件默认不预选目标阶段，链接存在本身不构成推进证据。

## 判定与匹配

- 优先判定强结果句和邮件主题主事件；条件句“若未通过”不能算淘汰，内推／宣讲／问卷不能算投递或面试。保存命中的脱敏证据句，不保存原始邮件正文或专属测试 URL。
- 邮件公司和岗位信息只用于推荐；在本浏览器的岗位中，只有公司正式名或受控别名和岗位名称同时明确命中且候选唯一时自动预选。仅公司命中、同公司多岗位、未知发件域、旧演示岗位、证据不足一律待核对，用户可手动选已有岗位。不自动新建岗位。
- 投递成功→已投递，测评邀请→测评，笔试邀请→笔试；泛称面试只可从面试前建议到一面，二面／三面／HR 面须邮件明确写出。已在相同或更后阶段的历史邮件不构成推进，终态冲突放待核对且须特别确认。
- 一封邮件在 UIDVALIDITY＋UID 下唯一；重复扫描不重复生成审批。批准较新阶段后，旧阶段建议仅显示已覆盖，绝不倒退。

## 数据与失败恢复

- `mail_scan_batches` 继续保存批次及招聘相关观察；未识别邮件仅保存最小元信息，防止规则假阴性变为用户不可见。GET 可恢复现有批次的候选观察。新增 `mail_review_decisions`（用户、邮箱 UIDVALIDITY、UID、状态、关联岗位、目标阶段、更新时间），RLS 开启且客户端无直连权限，读写均经受认证的 Node API。断开或重连邮箱时清除对应批次和决定。
- 当前浏览器 localStorage 中的岗位仍是事实源。首次邮件驱动修改前独立备份 `jobfind.jobs.backup.mail-v1`，不覆盖 V3 备份；应用时重新校验岗位存在和现阶段，写入带邮件事件 ID 的时间线以防重复应用。若服务端决定回执失败，本地显示已应用待同步并允许重试，不再次改变岗位。
- 已忽略与已应用决定在刷新／重复扫描后可恢复；“暂不处理”不落决定。其他浏览器若没有对应岗位，仅显示邮件，不得直接写入演示岗位。

## 界面

状态收件箱优先显示可操作数量和“查看与处理”入口；下方为“进度建议”“待核对”两个轻量分栏。每条显示公司／岗位（无法匹配则标明）、当前→建议阶段、主题和邮件时间。弹窗为紧凑队列＋证据详情，显示命中句、发件域、匹配依据、岗位与目标阶段选择。底部操作固定可见：暂不处理、忽略、应用到看板；不提供批量应用，不自动弹窗。窄屏单列，遵守视口高度。扫描后若有待处理项，入口和数量立即更新。

## 本期边界与验收

手动扫描触发；不含后台定时查信、不自动保存测试链接或截止时间、不扩展广告邮件文件夹。验证现有真实样本中的投递／测评／笔试／面试／淘汰可见，宣传和模糊邮件进入待核对或仅邮件列表；重复扫描、刷新、失败重试不重复推进；批准之前所有已有岗位保持原状。
